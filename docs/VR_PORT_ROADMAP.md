# Arx Fatalis VR — implementation roadmap

This document turns the current VR prototype into a campaign-playable standalone VR port.
It is intentionally implementation-oriented: every phase names the Arx subsystems to change,
reference projects to study, expected new modules, and acceptance gates.

## Definition of "full VR port"

A build is considered a full VR port when a player can start a new game, finish the complete
campaign, save/load, fight, cast spells, use inventory and quest UI, and interact with required
world objects using only the headset and tracked controllers. No keyboard, mouse, ADB command,
diagnostic teleport, forced script event, forced NPC death, collision override, or synthetic pose
may be required for the acceptance route.

The shipping path must keep a non-VR fallback for engine logic where practical, but VR input,
camera, rendering and interaction are first-class systems rather than mouse emulation.

## Current strengths

The repository already contains the expensive foundation:

- OpenXR session and Android standalone host
- tracked HMD and controller poses
- immersive stereo rendering
- room-scale head translation and physical crouch
- head-relative locomotion and snap turning
- tracked hand models and finger curl
- world-space menu pointing
- physical mesh-based grabbing
- object rotation while held
- release velocity and throwing
- fist combat
- held-object combat
- rune drawing driven by controller motion
- normal Arx script interaction fallback

The roadmap therefore focuses on productionising these systems rather than rewriting them.

# Phase 0 — Separate diagnostic automation from real VR acceptance

## Goal

Make it impossible to confuse an integration shortcut with proof that the game is physically
playable in VR.

## Arx files

- `ArxAndroid/src/core/ArxGame.cpp`
- `ArxAndroid/src/vr/AndroidVrInput.cpp`
- `ArxAndroid/src/vr/AndroidVrEngine.cpp`
- `tools/run-arxvr-*.ps1`
- `diagnostics/`

## Changes

1. Keep `VrTraversalDiagnostic` as an integration-test facility only.
2. Add an explicit diagnostic capability bitmask:
   - synthetic pose
   - synthetic stick/button
   - world-state mutation
   - forced script event
   - forced damage/death
   - forced collision
   - forced level transition
3. Prefix all logs generated by shortcut-capable code with `ARXVR_DIAGNOSTIC_MUTATION`.
4. Create a separate acceptance runner that is allowed to send only:
   - tracked/synthetic HMD pose
   - tracked/synthetic controller pose
   - sticks
   - physical buttons
5. Acceptance reports must fail if a world-state mutation capability is armed.

## Acceptance gate

The jail escape route reaches the next normal location without any direct entity teleport,
`SM_ACTION` injection, `SM_HIT` injection, forced death, collision disable or forced downward
velocity.

# Phase 1 — Haptics as an engine service

## Reference

- Team Beef QuakeQuest: OpenXR vibration action and short selection ticks
- Team Beef JKXR: controller feedback tied to interaction state
- current PICO OpenXR host in this repository

## Existing Arx locations

- `PICO-OpenXR-Demos/app/src/main/cpp/openxr_program.cpp`
- `PICO-OpenXR-Demos/app/src/main/cpp/demos/application.cpp`
- `PICO-OpenXR-Demos/app/src/main/cpp/demos/application.h`

## New module

- `ArxAndroid/src/vr/VrHaptics.h`
- `ArxAndroid/src/vr/VrHaptics.cpp`

## Work

1. Fix callback ABI ordering and seconds-to-nanoseconds conversion.
2. Expose a small engine-to-host haptic queue rather than calling host code from gameplay sites.
3. Haptic event model:

```cpp
enum class VrHapticEventType {
    Grab,
    Release,
    UiTick,
    UiConfirm,
    ImpactLight,
    ImpactHeavy,
    Block,
    Parry,
    RuneAccepted,
    RuneRejected,
    SpellCast,
    BowString
};

struct VrHapticEvent {
    VrHand hand;
    VrHapticEventType type;
    float amplitude;
    float durationSeconds;
    float frequencyHz;
};
```

4. The OpenXR host consumes queued events once per frame and submits
   `xrApplyHapticFeedback`.
5. Gameplay code requests semantic events; it does not know OpenXR.

## Initial haptic mapping

- grip threshold crossed: 0.03–0.04 s, low amplitude
- object successfully attached: short confirmation pulse
- weapon/NPC impact: amplitude based on impact energy
- parry: sharp pulse in both controllers
- radial menu sector change: tiny tick
- valid rune: short crisp pulse
- invalid rune: double low pulse
- bow draw: optional low continuous feedback close to maximum draw

## Acceptance gate

A physical-controller test confirms distinct, non-stuck feedback for UI selection, grab, impact
and rune recognition on both hands.

# Phase 2 — Rendering: move toward a mobile-VR renderer

## Primary reference

Team Beef Doom3Quest:

- `app/src/main/jni/Doom3Quest/VrRenderer.c`
- `app/src/main/jni/Doom3Quest/VrFramebuffer.c`
- OpenGL ES texture-array / `GL_OVR_multiview`
- `glFramebufferTextureMultiviewOVR`
- `glFramebufferTextureMultisampleMultiviewOVR`

## Current Arx files

- `PICO-OpenXR-Demos/app/src/main/cpp/demos/application.cpp`
- `PICO-OpenXR-Demos/app/src/main/cpp/graphicsplugin_opengles.cpp`
- `ArxAndroid/src/core/ArxGame.cpp`
- Arx legacy renderer / GL4ES path

## Workstream A — instrumentation first

Record separately:

- game simulation CPU
- scene preparation CPU
- left-eye draw CPU/GPU
- right-eye draw CPU/GPU
- transparent pass
- particles/spells
- hands
- UI
- compositor submit
- dropped frames

Do not optimize from screenshots or average frame time alone.

## Workstream B — MultiView prototype

Create an experimental renderer path behind a build/runtime flag.

Suggested new module:

- `PICO-OpenXR-Demos/app/src/main/cpp/arxvr_multiview_renderer.{h,cpp}`

Prototype requirements:

1. Allocate a 2-layer color texture array.
2. Allocate a compatible depth texture array.
3. Attach both views using `GL_OVR_multiview`.
4. Export two view/projection matrices to the engine in one frame.
5. Keep simulation/update strictly once per frame.
6. Render scene geometry to both views in one render traversal where shaders allow it.
7. Preserve the current dual-pass path as fallback until visual parity is proven.

The difficult part is GL4ES and fixed/legacy pipeline compatibility. If direct MultiView cannot be
made reliable without rewriting most shaders, retain dual-eye drawing and first optimize shared
scene preparation, culling and state changes.

## Workstream C — standalone-specific optimisations

After correctness:

- fixed foveated rendering where the runtime exposes it
- dynamic render scale
- PICO adaptive resolution where available
- material/transparency audit
- particle overdraw limits
- LOD and distance limits appropriate to headset resolution
- avoid rebuilding shared visibility between eyes
- avoid CPU-side state updates on secondary eye
- batch UI and hand rendering separately

## Acceptance gate

Target is stable headset-refresh pacing in representative combat and spell-heavy scenes, not only
the opening jail. The performance suite must include at least one crowded room, one spell-heavy
fight, inventory UI, and a 20+ minute thermal run.

# Phase 4 — Normalise physical interaction into a reusable subsystem

## References

- HIGGS interaction model
- PLANCK physical-character contact model
- current Arx `Dragging.cpp`

## Current Arx files

- `ArxAndroid/src/gui/Dragging.cpp`
- `ArxAndroid/src/core/ArxGame.cpp`
- `ArxAndroid/src/vr/AndroidVrInput.cpp`

## New modules

- `ArxAndroid/src/vr/VrInteractionSystem.{h,cpp}`
- `ArxAndroid/src/vr/VrImpact.{h,cpp}`
- `ArxAndroid/src/vr/VrHandState.{h,cpp}`

## Move out of ArxGame.cpp

- target selection
- physical grab state
- fist state
- held-object impact state
- hand velocity history
- interaction prompts
- aim-assist decisions

## Common impact representation

```cpp
enum class VrImpactType {
    Fist,
    HeldObject,
    EquippedWeapon,
    Shield,
    Projectile
};

struct VrImpactEvent {
    EntityHandle attacker;
    EntityHandle target;
    EntityHandle weapon;
    VrHand hand;
    VrImpactType type;
    Vec3f position;
    Vec3f direction;
    Vec3f linearVelocity;
    Vec3f angularVelocity;
    float effectiveMass;
    float pathLength;
};
```

Combat code converts this event into existing Arx damage/script/sound behaviour.

## Anti-waggle rules

Do not use instantaneous speed as the only damage input.

Track:

- minimum swing path length
- peak and average velocity
- impact angle
- time since previous valid impact
- weapon mass/category
- reset distance after a hit

This prevents high-frequency wrist shaking from becoming optimal combat.

## Acceptance gate

Fist, bone, chair and a normal equipped melee weapon all pass through the same impact pipeline.

# Phase 5 — Equipped melee weapons, shields, block and parry

## Primary reference

JKXR:

- `Projects/Android/jni/OpenJK/JKXR/VrInputDefault.cpp`
- `Projects/Android/jni/OpenJK/JKXR/VrInputWeaponAlign.cpp`

Useful ideas:

- per-controller orientation correction
- per-weapon alignment profile
- dominant/off-hand separation
- two-handed stabilisation
- controller velocity driven melee
- debounce after contact/block

## New modules

- `ArxAndroid/src/vr/VrWeaponSystem.{h,cpp}`
- `ArxAndroid/src/vr/VrWeaponProfile.{h,cpp}`

## Weapon profile

```cpp
struct VrWeaponProfile {
    Vec3f gripOffset;
    Anglef gripAngles;
    Vec3f secondaryGripLocal;
    float minimumSwingSpeed;
    float minimumSwingPath;
    float effectiveMass;
    float tipDamageMultiplier;
    bool supportsTwoHand;
};
```

Provide defaults by geometry and optional overrides for named weapons.

## One-handed weapon flow

inventory/equip
→ attach weapon model to dominant hand
→ apply weapon profile
→ update from controller grip pose
→ sweep damaging segment/mesh
→ emit `VrImpactEvent`

## Two-handed flow

When off-hand grip is pressed near a valid secondary-grip region:

- enter two-hand constraint
- weapon direction follows the vector between hands
- dominant hand remains primary pivot
- release off-hand returns smoothly to one-hand mode

## Shield

- attach to off-hand
- physical shield volume
- block based on incoming direction and shield plane
- impact haptic on off-hand
- no damage or reduced damage according to existing Arx rules

## Parry

Weapon-vs-weapon contact creates a parry event when relative velocity and angle exceed thresholds.
Apply haptic pulse, collision sound and a short attack debounce.

## Acceptance gate

A player can defeat an early enemy using equipped sword/mace and can block at least one normal
enemy melee attack with a shield, without pressing the legacy attack key.

# Phase 6 — Bow and projectile weapons

## References

- common VR bow interaction pattern
- JKXR two-hand transform logic
- MageVR quiver interaction concept

## New module

- `ArxAndroid/src/vr/VrBowSystem.{h,cpp}`

## Flow

1. Bow is held in one hand.
2. Other hand grabs a string/nock interaction zone.
3. Draw distance is measured between bow anchor and string hand.
4. Draw distance maps to original Arx bow charge/strength.
5. Bow orientation is derived from both hands.
6. Release launches the original Arx projectile using physical direction and draw strength.

Optional later:

- shoulder quiver grab
- visible arrow nock
- string mesh deformation

## Acceptance gate

Bow combat works through physical draw/release and still respects original stats, ammunition and
damage logic.

# Phase 7 — Magic: make Arx's rune system the signature VR mechanic

## Reference

MageVR glyph casting, while retaining Arx's native rune recognition.

## Current files

- `ArxAndroid/src/vr/AndroidVrInput.cpp`
- `ArxAndroid/src/core/ArxGame.cpp`
- Arx spell/rune recogniser

## Work

The current `Y + right trigger + hand movement` path already feeds rune points. Productionise it:

1. Decouple rune sampling from screen-space assumptions where possible.
2. Add a stable virtual drawing plane in front of the player or hand-relative plane.
3. Render the rune trail in 3D or a correctly stereo-projected overlay.
4. Add accepted/rejected rune haptics.
5. Show recognised rune glyph briefly near the casting hand.
6. Direct targeted/projectile spells from the casting hand.
7. Use hand direction for projectile orientation.
8. Preserve original spell costs, prerequisites, script effects and timing.
9. Add an optional quick-spell radial menu without removing freehand rune casting.

## Acceptance gate

A spell sequence can be drawn, recognised and cast entirely by tracked hand motion; projectile
spells visibly originate from the casting hand.

# Phase 9 — Physical RPG interactions

These are high-value interactions that remove repeated menu use.

## Consumables

Potion/food held near the head/mouth interaction sphere triggers the original item-use logic.

Requirements:

- require deliberate grip/pose
- small dwell or velocity gate to prevent accidental use
- consume through normal inventory/script path

## Body slots / quick storage

Optional later stage:

- shoulder weapon slot
- back slot
- belt slots
- potion slot
- quiver

The underlying inventory remains canonical; body slots are only fast equip/use affordances.

## Torches

A held/equipped torch follows the physical hand. Dynamic light origin follows the torch model.

## Acceptance gate

At least potion, food and torch have natural physical use without opening inventory every time.

# Phase 10 — World interactions

Keep the current generic controller-ray + original Arx script fallback for complete compatibility.

Add physical profiles only for common, high-value objects:

- lever
- door handle
- chest lid
- buttons
- movable quest props

Important principle: a physical interaction must ultimately call the same original script/action path
that normal Arx uses, unless the original mechanic cannot express the required state.

## Acceptance gate

Every mandatory campaign interaction is reachable either by a physical profile or the generic
controller interaction fallback.

# Recommended implementation order

The order below minimises risk and maximises usable progress:

1. Real-controller acceptance harness
2. Haptics bug fixes and semantic haptic service
3. VR config + seated/standing calibration
4. Extract interaction/impact systems from `ArxGame.cpp`
5. Equipped melee weapon in dominant hand
6. Two-handed weapon + shield/block
7. Rune-casting production pass
8. VR book/inventory panel
9. Quake-style radial selection
10. Bow
11. Consumables and quick body interactions
12. Doom3Quest-inspired MultiView prototype in parallel with gameplay work
13. Performance/thermal optimisation
14. Full campaign matrix and completion
15. Polish

Rendering work should run in parallel after instrumentation because MultiView may require a larger
renderer refactor. Gameplay completion must not be blocked waiting for that experiment.

# Release gates

## VR Alpha

- real tracking works
- complete first level physically playable
- grab/throw stable
- basic melee weapon works
- rune spell can be cast
- book/inventory usable
- save/load usable

## VR Beta

- melee/shield/bow/magic complete
- seated mode
- radial menus
- all mandatory world interactions mapped
- campaign completion achieved at least once
- representative scenes meet acceptable frame pacing

## 1.0

- repeated campaign completion
- no progression blockers
- stable save/load
- controller loss/reconnect safe
- focus/system-dashboard recovery safe
- sustained thermal/performance pass
- comfort and handedness options
- no diagnostic shortcut required for normal play
